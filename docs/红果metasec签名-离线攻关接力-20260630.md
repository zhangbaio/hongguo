# 红果 metasec 签名 · 纯离线攻关接力文档(2026-06-30)

目标:在桌面/服务器**脱离 app** 生成红果(`com.phoenix.read`, aid=8662)的请求签名
(`X-Argus/X-Gorgon/X-Ladon/X-Khronos/X-Helios/X-Medusa/...`),从而离线完成 device_register
及任何需 aid-8662 签名的接口。

> 现状:**功能已不依赖它**——内容/搜索/榜单/下载用"跨 app 签名"(番茄海外签名器)已通,
> 设备用 `grab_device.py`(让真 app 注册后抓设备)已通,解密全离线。本文件只为攻克"红果自身离线签名"这一研究目标接力。

---

## 1. 已验证可用的参照(番茄海外,同 metasec 家族)

- `unidbg-sign/FqTrace.java`:unidbg 跑番茄海外 `libmetasec_ml.so`,**直调内部签名函数 offset `0x168c80`**,
  传 `(url, header)` → 返回完整签名头。**已端到端验证**(线上脱机签名服务即用它)。
- 番茄库 ≠ 红果库(版本/build 不同):番茄 3447432B(md5 `affd5bdf…`),红果 3971808B(md5 `a2b9619c0761b8a6f74cb346eb86cddd`),
  `0x168c80` 处字节完全不同 → **番茄 offset 对红果无效**,需找红果自己的签名函数。
- Linux 运行:默认 unicorn1 native 缺 helper 符号;改用 **Unicorn2 后端**(`unidbg-unicorn2` 依赖 + `Unicorn2Factory`),
  其 `natives/linux_64/libunicorn.so` 自洽。详见 deploy/全栈上云 + xinge 脱机直连提交。

## 2. 红果 libmetasec_ml.so 已锁定的情报

文件:设备 `/data/app/.../lib/arm64/libmetasec_ml.so`(= `capture/so/libmetasec_ml.so`,3971808B,md5 `a2b9619c…`)。
APK 内 `lib/arm64-v8a/libmetasec_ml.so` 是**不同的 stub**(无下述字符串),必须用设备真身。

| 项 | 值 | 来源 |
|---|---|---|
| **签名命令名锚点** | 字符串 `ML_DoHttpReqSignIT` | strings,文件偏移 `0x37bbaa`,VA 偏移 `0x383baa`(Ghidra imagebase 0x100000 时 = 0x483baa) |
| **native 分发器** | JNI 方法 `a(IIJLjava/lang/String;Ljava/lang/Object;)Ljava/lang/Object;` → `libmetasec_ml.so + 0x26e684` | hook RegisterNatives(JNIEnv 表索引215)spawn 时捕获 |
| `.text` 范围 | `0x15db00 – 0x347e64` | ELF section |
| 证书(op 16777218)| = **hex 字符串(DER 证书)**;番茄的解码后是 Oplus/AndroidTeam 设备平台证书(1007B);**红果的待定** | 解码番茄 `ms_16777218.bin` 确认 |
| MS.b 回调(native→java)| 65539=files/.msdata路径; 16777218=证书; 16777232=versionCode(72232); 16777233=版本"7.2.2.32"; 268435470=currentTimeMillis; 33554433/4=true; MS.a()=0x40 | FqTrace 模板(番茄)+ 红果实测 op 一致 |

**关键结构发现:红果请求签名是 native-to-native** —— libsscronet(cronet 网络层)直接调 libmetasec 的签名函数,
**不经过 JNI 分发器 `a`**(已三次验证:`a` 的 op 只有 16777217/0x200000d/0x3000003,均不带 url;arg5 String、arg6 Object、arg4 long 指针均非请求数据)。
故 hook JNI 抓不到签名;签名函数只能从 native 侧定位。

## 3. 已穷尽的死路(勿重走)

定位"引用 `ML_DoHttpReqSignIT` 的函数"= 定位签名函数(或其路由),但:
- **静态 xref 全 0**:① 二进制内无指向 VA `0x383baa` 的 8 字节字面指针;② `.rela.dyn` 无 addend==0x383baa 的 RELATIVE 重定位;
  ③ 无 `ADD Xd,Xn,#0xbaa`(字符串低12位)指令;④ Ghidra 12.1.1 自动分析后 `getReferencesTo` = 0。
  → OLLVM 把字符串地址计算彻底混淆/运行时算出,静态恢复不了。
- **动态 watchpoint 不可行**:frida 17.9.6 无 `Thread/Process.setHardwareWatchpoint`;`MemoryAccessMonitor` 是页粒度+只报每页首次访问,
  目标串所在 .rodata 页极热,抓不到签名那次读取。
- **二进制 diff / .rodata 表匹配**(对番茄 0x168c80)早期失败:VM 字节码表是 per-build 的。
- **跨库喂证书**:番茄证书是 Oplus 设备证,红果 op-16777218 返回什么未确认。

## 4. 推荐的接力路线(需 IDA / 专门 RE 环境)

按成功率排序:
1. **IDA Pro 找 `ML_DoHttpReqSignIT` 的 xref**:IDA 对 OLLVM 的混淆地址计算(ADRP + 多步算术)跟踪比 Ghidra 强,
   很可能直接给出引用该串的函数 → 即签名函数/路由。拿到 `函数偏移`。
2. **内核/ptrace 硬件 watchpoint** 盯字符串运行时地址(base+0x383baa),app 发一次请求 → 捕获访问指令 PC → 所在函数。
   (frida 不行,需 gdb/lldb-server 或自写 ptrace 工具,arm64 DBGWVR/DBGWCR。)
3. **Stalker 边界调用追踪**:Stalker.follow 网络线程,`events:{call:true}`,过滤 target∈libmetasec 且 from∉libmetasec
   = cronet→metasec 入口,签名函数在其中。(重、字节系反调试,易崩,谨慎。)
4. **OLLVM 去虚拟化** `0x26e684` 分发器 / 签名函数(研究级,最后手段)。

### 拿到签名函数 offset 后(harness 已就绪)
- `unidbg-sign/MetasecSign.java`(红果 harness):类链 `ms/bd/c/m ← a4$a ← MS` + MS.b 回调已写好。
  把 `SIGN_OFFSET` 改成定位到的红果 offset。
- **证书**:确定红果 op-16777218 返回值。两种取法:① fresh `pm clear` 后 hook `MS.b(16777218)` 返回(只在首次注册触发,时序飘);
  ② 先试番茄的 Oplus 证(若是设备级则通用)。证书是 hex(DER) 格式,塞进 `handleMS(16777218)`。
- **版本/时间**:versionCode 72232、版本 "7.2.2.32"、时间用注入的 currentTimeMillis(保证可复现)。
- 验证:产出 `X-Argus` → 用 `device_register_offline.py` 打 `log.snssdk.com/service/2/device_register/?tt_data=a`,
  看返回 `device_id_str` 非 0(applog 网关严格校验 X-Argus 内 aid=8662)。
