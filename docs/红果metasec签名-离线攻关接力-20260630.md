## 2. 红果 libmetasec_ml.so 已锁定的情报

文件:设备 `/data/app/.../lib/arm64/libmetasec_ml.so`(= `capture/so/libmetasec_ml.so`,3971808B,md5 `a2b9619c…`)。
APK 内 `lib/arm64-v8a/libmetasec_ml.so` 是**不同的 stub**(无下述字符串),必须用设备真身。

| 项 | 值 | 来源 |
|---|---|---|
| **签名命令名锚点** | 字符串 `ML_DoHttpReqSignIT` | strings,文件偏移 `0x37bbaa`,VA 偏移 `0x383baa`(Ghidra imagebase 0x100000 时 = 0x483baa) |
| **native 分发器** | JNI 方法 `a(IIJLjava/lang/String;Ljava/lang/Object;)Ljava/lang/Object;` → `libmetasec_ml.so + 0x26e684` | hook RegisterNatives(JNIEnv 表索引215)spawn 时捕获 |
| `.text` 范围 | `0x15db00 – 0x347e64` | ELF section |
| 证书(op 16777218)| = **hex 字符串(DER 证书)**;番茄的解码后是 Oplus/AndroidTeam 设备平台证书(1007B);**红果的待定** | 解码番茄 `ms_16777218.bin` 确认 |
| MS.b 回调(native→java)| 65539=files/.msdata路径; 16777218=证书; 16777232=versionCode(72232); 16777233=版本"7.2.2.32"; 268435470=currentTimeMillis; 33554433/4=true; MS.a()=0x40 | FqTrace 模板(番茄)+ 红果实测 op 一致 |

**关键结构发现:红果请求签名是 native-to-native** —— libsscronet(cronet 网络层)直接调 libmetasec 的签名函数,
**不经过 JNI 分发器 `a`**(已三次验证:`a` 的 op 只有 16777217/0x200000d/0x3000003,均不带 url;arg5 String、arg6 Object、arg4 long 指针均非请求数据)。
故 hook JNI 抓不到签名;签名函数只能从 native 侧定位。

## 3. 已穷尽的死路(勿重走)

定位"引用 `ML_DoHttpReqSignIT` 的函数"= 定位签名函数(或其路由),但:
- **静态 xref 全 0**:① 二进制内无指向 VA `0x383baa` 的 8 字节字面指针;② `.rela.dyn` 无 addend==0x383baa 的 RELATIVE 重定位;
  ③ 无 `ADD Xd,Xn,#0xbaa`(字符串低12位)指令;④ Ghidra 12.1.1 自动分析后 `getReferencesTo` = 0。
  → OLLVM 把字符串地址计算彻底混淆/运行时算出,静态恢复不了。
- **动态 watchpoint 不可行**:frida 17.9.6 无 `Thread/Process.setHardwareWatchpoint`;`MemoryAccessMonitor` 是页粒度+只报每页首次访问,
  目标串所在 .rodata 页极热,抓不到签名那次读取。
- **二进制 diff / .rodata 表匹配**(对番茄 0x168c80)早期失败:VM 字节码表是 per-build 的。
- **跨库喂证书**:番茄证书是 Oplus 设备证,红果 op-16777218 返回什么未确认。

## 4. 推荐的接力路线(需 IDA / 专门 RE 环境)

按成功率排序:
1. **IDA Pro 找 `ML_DoHttpReqSignIT` 的 xref**:IDA 对 OLLVM 的混淆地址计算(ADRP + 多步算术)跟踪比 Ghidra 强,
   很可能直接给出引用该串的函数 → 即签名函数/路由。拿到 `函数偏移`。

## 4b. 第二轮攻关新情报(2026-06-30 晚)—— **重大进展:拿到 libsscronet**

**核心转向**:签名头(`x-argus/x-gorgon/x-ladon/x-khronos`)的字符串**在 libsscronet.so 里,不在 libmetasec**。
即 **libsscronet 才是构建签名头、编排签名的一方**,它调 libmetasec 内部 sign 函数拿加密结果。
libsscronet 是**标准 cronet build,非 OLLVM 混淆**——这是新突破口(比啃混淆的 metasec 容易)。

新拉取资产(从设备,gitignore):`capture/cronet/libsscronet.so`(6192768B)、`capture/cronet/libmetasec_dev.so`(=红果真身,md5 `a2b9619c…` 与 capture/so 一致)。
设备路径 `/data/app/~~TP5wJd7a…/com.phoenix.read-…/lib/arm64/`。

**已锁定事实**:
- 红果 libmetasec **dynsym 只导出 `JNI_OnLoad`**(导出函数=1)。故 sign 函数靠**运行时解析的指针**被调,不可能有静态符号 xref——彻底解释为何静态 xref 全 0。
- metasec **不 dlsym cronet 符号**;它只 dlsym 了 `dl_iterate_phdr`(调用点 `libmetasec+0x204794`),用来遍历已加载模块找 libsscronet 等基址做 **native 集成**(算偏移直调,无符号)。
- cronet 的 `Cronet_ClientOpaqueData_do_sign_set/get`(`str x1,[x0,#0x68]` / `ldr x0,[x0,#0x68]`)是 **mTLS 客户端证书签名**(邻居导出全是 private_key/certificate/algorithm_prefer),**与 X-Argus 头签名无关,已排除**。
- **请求签名不回调 Java `MS.b`**(hook JNIEnv CallStatic*Method 过滤返回地址∈metasec,触发请求时只见分发器区 `metasec+0x26e9bc/+0x26f95c` 的心跳/上报回调 op=131074/16777246/54/55,**无深层 .text 回调**)→ 证书/版本在 init 后已缓存,签名时不回 Java。**MS.b 追踪法对请求签名无效。**
- libsscronet 头名字符串 VA:`x-argus`@0x7337c、`x-khronos`@0x74785、`x-gorgon`@0x7a210、`x-ladon`@0x7a219。
  对这些串:rela.dyn addend / 8字节字面指针 / 朴素 ADRP+ADD 单遍扫描 **均 0**(同 metasec 的 ML 串),需 Ghidra/IDA 正经分析(大字符串表基址+偏移寻址,朴素扫描器抓不到)。

**公开情报(看雪/知乎,抖音同源)**:libsscronet 内参数签名序列(抖音版偏移,供类比)`X-Argus@0x7d3f0`、`X-Ladon@0x7dd18`、`X-Gorgon@0x811a8`、key 加密@0x7e530;libmetasec `X-Gorgon sub_14DBF4@0x14DBF4`。
→ 红果 libsscronet 的编排函数应在头名串(0x73000–0x7a000)之后的 **~0x7b000–0x83000** 区(`GhidraFindXargus.java` 正在查)。

**新推荐路线(最高 EV,用新资产)**:
1. **Ghidra/IDA 分析非混淆的 libsscronet**:找引用 `x-argus` 串的编排函数 → 它内部对 libmetasec 的**间接调用(blr 经全局函数指针)**= sign 入口;该全局指针在 libsscronet .bss/.data,**运行时读出即得 metasec sign 偏移**。脚本 `unidbg-sign/GhidraFindXargus.java`。
2. **unidbg ReadHook/CodeHook 是字节粒度**(frida 17 无硬件 watchpoint 的替代):FqTrace 已有 `enableReadTrace`(ReadHook 统计热读地址);可扩展为抓"读 X 地址时的 PC"(`backend.reg_read(PC)`)定位访问指令。番茄实测调 0x168c80 热读表在 `+0x2e6223..+0x2e6272`。
3. 动态读全局指针:在 libsscronet 编排函数定位到"调 metasec 的 blr 经 [global]"后,frida 读该 global = 运行时 metasec sign 地址,减基址=偏移。

**工具就绪**:`unidbg-sign/scan_mlref.py`(ARM64 ADRP+ADD/LDR + 偏移表 + hash 常量扫描器,需 capstone+pyelftools)、`frida/hook_dosign.js`(do_sign,已证 mTLS 无关)、`frida/hook_msb.js`(MS.b+JNIEnv 表 hook)、`frida/hook_dlsym.js`(metasec dlsym 监控)、`unidbg-sign/GhidraFindXargus.java`。

## 7. ✅ 攻克(2026-06-30 晚)—— 红果 aid-8662 签名已破,设备后端端到端验证 code=0

**签名函数 = `libmetasec_ml.so + 0x27d288`**(标准 ARM64 函数序言 `sub sp,sp,#0xc0;...;mov x20,x0`)。

**定位法(决定性)**:metasec 只导出 JNI_OnLoad,用 `dl_iterate_phdr`(@metasec+0x204794)找 libsscronet 基址后,把自己的 sign 函数指针**直接写进 libsscronet 的可写数据段**(非导出、非 dlsym、非 cronet 注册API,故前面所有招都抓不到)。
→ frida 扫 libsscronet rw 段中落在 libmetasec 区间的指针即得(`frida/scan_cronet_data.js`):
- `sscronet+0x5f5458 → metasec+0x27d288` = **请求签名**(X-Argus/Gorgon/Ladon/Helios/Khronos/Medusa/Neptune)
- `sscronet+0x5f5470 → metasec+0x27d950` = **X-Cylons 签名**(websocket/frontier)

**调用约定**(动态实测 + 探针确认):
`ret = sign(x0=url_cstr, x1=header_cstr, x2=0x18, x3=ns_tick, x4=0xffffffffffffff, x5=counter, x6=0, x7=0)`
返回 char* `"X-Argus\r\n<val>\r\nX-Gorgon\r\n<val>\r\n..."`。探针结论:
- **x0(url)可任意替换** → 能签任意请求。
- **x1(header)必须非空 + 完整 `key\r\nvalue\r\n` 对**(奇数段/空 → 返回 null)。
- **x2=0x18、x4=0xffffffffffffff 是常量**;x3(ns 单调 tick)、x5(计数器)递增即可;**x6/x7 无关**(实测清零仍出有效签名,之前看到的 "gzip,deflate" 是寄存器残留)。
- X-Argus/X-Khronos 随时间窗(秒)变;X-Gorgon/Ladon/Helios/Medusa 随 url+header 变。

**工作签名器(设备后端,已验证)**:
- `frida/sign_service.js`：`rpc.exports.sign(url, header)` 调 0x27d288。
- `frida/hongguo_sign_server.py`：HTTP `POST /sign {url,headers}→{X-Argus..}`(FqTrace 协议,`SIGN_SERVER` 兼容,app 重启自动重连)。
- **端到端验证**(`frida/validate_sign.py`)：签名真实 search 请求 → fqnovel 返回 `code=0 SUCCESS` + 真实结果。✅
- 用法：`adb` 可达 + frida-server 在设备 + 红果 app 前台 → `python3 frida/hongguo_sign_server.py 9101`,然后 `export SIGN_SERVER=http://127.0.0.1:9101`。
- **价值**：红果自身 aid=8662 签名 > 番茄跨app(后者 device_register/applog 因 aid 不符被拒)。此签名器可签 applog,理论上能离线注册红果设备。

**调试链(可复现)**：`hook_dosign.js`(do_sign=mTLS排除)→`hook_msb.js`(请求签名不回调MS.b)→`hook_dlsym.js`(metasec用dl_iterate_phdr不dlsym cronet)→`hook_sweep.js`(注册非经导出)→`scan_cronet_data.js`(命中2指针)→`hook_signcand.js`(确认0x27d288=sign,dump参数)→`grab_groundtruth.js`(完整样本)→`replay_sign.js`/`probe_args.js`/`probe_hdr.js`(确定调用约定)→`hongguo_sign_server.py`(成品)。

### 7b. device_register 离线注册测试结论(2026-06-30)
用 `0x27d288` 原生签名跑 `device_register_offline.py`(SIGN_SERVER=红果签名器9101 + EncryptRun9100):
- **签名被 applog 网关接受**(返回 `server_time`,不再像番茄跨app那样被拒)——证明 aid=8662 校验通过,这是相对番茄跨app的实质进步。
- **但 `device_id=0, new_user=0`**:注册体每次用**随机** openudid/clientudid/cdid,服务端仍判 `new_user=0` → 它认出了**签名里绑定的设备身份**(本机已注册的 device_id)。
- **根本限制**:设备后端签名器用的是**运行中 app 已初始化的 metasec 状态**(绑定本机真实 device_id),X-Argus 反映"已注册设备"→ 服务端不给铸新设备。
- **要离线铸新红果设备**:须用 **fresh metasec 状态(device_id=0)** 签名——即第8节被阻的 unidbg fresh-init;设备后端签名器做不到(身份绑定)。务实路线仍是 `grab_device`(真 app 注册后抓设备入池)。
- host:红果 applog = `log5-applog-lq.fqnovel.com/service/2/...`(非 log.snssdk.com)。

### 7c. 设备指纹去重测试(2026-06-30)—— 铸新设备需改硬件指纹

## 8. 纯离线(unidbg)残留 —— init 状态未就位

`MetasecSign.java` 已填 `SIGN_OFFSET=0x27d288` + 6 参调用 + `driveInit()`(调分发器 `a(0x4000001, config)`,config=`capture/cronet/init_config.json` 含 license `["8662","","",<license>,"v04.09.09.01-bugfix","update_64",...]`)。
现状:init 返回 `true` 但**没打开 .msp/.mss 状态文件**(没加载证书/算法表)→ sign 返回 null。
原因:设备上 init 是多步握手(分发器 `a` 在 #8 主 init 前有 #1–#7:op `0x1000003/0x5000001/0x4000002/0x1000001(带hex串+Java obj)/0x3000003` 等),部分调用带 **Java 对象参数**(SDK 内部对象),unidbg 难直接构造。
设备 `.msdata` 状态已拉 `capture/msstate/`(但 unidbg 算出的状态文件 hash 名与设备的不符 → 即便提供也加载不上,说明 init 参数/上下文未完全对齐)。
接力点:① 用 frida 抓 #1–#8 各调用的 Java obj 参数内容并在 unidbg 复现;或 ② 设备内存快照 metasec 已初始化的 .data/.bss(注意内嵌指针重定位);或 ③ 直接采用第7节设备后端方案(已可用)。

## 9. 2026-07-02 Path B 深挖 —— 精确定位到"fresh 注册创建 .msp bootstrap store"这堵墙

用 `MetasecSign`(已对齐设备版本 7.2.5.32/vc72532 + 加 resolve/op 日志 + `-Dnoinit` 开关)逐帧看 init+sign 的 native↔Java 交互,把卡点从"init 状态没就位"精确到具体机制:

### 9.1 红果 7.2.5.32 metasec 用 `.msp_<sha1>` 缓存文件,不用 op-16777218 证书回调
- init(op 0x4000001)与 sign 都会:问 `MS.b(0x10003)` 拿 `.msdata` 路径 → **open `/.msdata/mssdk/ml/.msp_<hash>`(O_RDONLY)** → 读证书态。
- **全程不请求 op 16777218**(番茄海外 6.8.1.32 那套 cert 回调)。`-Dnoinit`(仿 FqTrace 惰性 init)行为一致 → **FqTrace 的打法对红果新 SDK 不通用**。这解释了为何 FqTrace(番茄)成而 MetasecSign(红果)败:两代 SDK 证书机制不同。
- sign 时另调 `MS.b(0x2000001)`、`MS.b(0x2000002)`(返回 true),读不到有效 .msp → **sign 返回 null**。

### 9.2 unidbg 请求的 .msp 名 = `SHA1(aid)`,但设备存在别的 key 下
- **已逆出**:unidbg init 请求的 `.msp_f06eb8f4a39e34a99b5513faa6b4527d2e18c498` = **`SHA1("8662")`**(精确匹配,非巧合)。sign 请求的 `.msp_3dddca0f...` 输入未逆出(非 aid 简单拼接,含内部盐/二进制)。
- **改 versionCode 72232→72532 hash 不变** → hash 输入不含 versionCode。
- **活体设备 + 06-30 快照都没有 `.msp_SHA1(aid)`**,只有设备绑定命名的 `.msp_092fde7a`/`.msp_589c2233`(+ 一堆 .mss/.msf3/.msfs)。→ 设备用**已初始化后派生的设备态 key** 命名,unidbg fresh 态回退到 `SHA1(aid)` 的 **bootstrap store**。

### 9.3 设备 .msp 是设备上下文绑定的,搬不过来
- 实验:把设备 `.msp_092fde7a`/`589c2233` 内容别名成 unidbg 请求的 `f06eb8f4`/`3dddca0f`,resolve 命中、metasec 读了文件,**但 sign 仍 null 且不再往下读 .mss/.msf3** → metasec 校验/解密 .msp **失败**(内容按设备上下文加密,hash 不同=内部密钥不同)。→ **objective-1(离线签"现有设备")也需复现设备完整上下文,非改名可得。**

### 9.4 完整图景 & 真正的墙
```
fresh metasec (unidbg) → open .msp_SHA1(aid)[bootstrap] → 不存在
   → 应做 fresh 注册: 建 bootstrap store → 派生设备态 store → 写 .msp → 可签
   → 但 unidbg 没做(无网络/无注册握手)→ 读不到 .msp → sign null
device metasec → 早已 fresh 注册过 → 只剩设备态 store(092fde7a..) → 正常签
```
**真正的墙 = 复现 metasec 的 "fresh 设备注册"**(建 bootstrap .msp store):很可能是 **网络握手(向字节 cert 服务器要证书)+ VM 保护的本地 crypto**。这就是文档反复提到的"metasec VM 反虚拟化",研究级、高不确定性。

### 9.5 下一步候选(按性价比)
1. **抓 fresh 注册网络流**:`pm clear` 红果 → 首启 → frida 抓 metasec 建 bootstrap .msp 时的网络请求(host/body/响应)+ 落盘的 .msp 内容,理解"证书从哪来"。若是纯网络换证书 → 可离线复刻;若掺 VM 本地 crypto → 难。
2. **objective-1 妥协**:复现设备上下文(device_id 等)喂 unidbg,让它算出设备的 .msp hash 并成功解密设备 .msp → 得到"现有设备的离线签名器"(脱离 frida/模拟器,但仍 1 台,不扩池)。
3. 维持现状:设备后端签名器可用;runtime 已离线。

### 9.6 本次改动的文件
- `unidbg-sign/.../MetasecSign.java`:VER→7.2.5.32、op16777232→72532、handleMS/resolve 加日志、`-Dnoinit` 开关。

1. **op-16777218 证书 fresh 注册时也不触发,全程无任何 byte[] 返回** → 红果 7.2.5.32 **不经 MS.b 交付证书**(FqTrace/番茄海外那套 cert 回调彻底不适用)。证书只能来自**网络握手**(metasec 向字节 cert 服务器注册换证)**或内部生成**。
2. **metasec init 查 ~50 个设备属性 op**(见存档)。关键:`op 16777250`=`b41c1245885f9e8da0b8094d843d08b7`(32hex,**被查 69 次**,疑核心设备密钥/指纹)、`op 16777253`=UUID、`op 16777263`=build 指纹、`op 16777266`=build props JSON、`op 16777232`=72532、`op 268435457`=1080*2400 等。unidbg 的 handleMS 对这些大多返 null → 这就是 unidbg 与设备行为分叉的根因。
3. **.msp 名是设备稳定值**:`pm clear` 重新 fresh 注册后 .msp 名仍是 `092fde7a`/`589c2233`(与之前完全一致)→ hash 输入=设备指纹属性(非随机盐)。unidbg 因属性返 null 回退到 `SHA1(aid)`=f06eb8f4。**但 hash 输入非已知属性的简单拼接**(暴力试 8662±各属性±分隔符全不中,含内部盐/二进制/未采集值)。

**objective-1(离线签现有设备)路径**:把设备 ~50 属性值全喂 unidbg handleMS → 期望它算出 092fde7a → 加载设备 .msp。风险:①hash 输入还含未知盐 ②.msp 可能用硬件派生 key 加密(unidbg 重现不了)。
**objective-2(扩池/铸新)额外需**:搞清证书来源。**下一步**:①frida hook metasec 算 .msp 名时的 native SHA1 输入(VM 混淆,难定位)②`pm clear` 后 hook 网络(cronet/socket send)抓 fresh 注册的 cert 握手(host/body/响应)——判"纯网络换证(可离线复刻)vs 掺 VM 本地 crypto(继续啃)"。

**结论**:红果 7.2.5.32 比番茄海外 6.8.1.32 硬一个量级(证书从"回调可喂"变成"设备绑定 .msp + 网络/内部生成")。真·离线铸设备 = 复现 metasec fresh 注册证书握手 + 设备上下文,研究级、多会话。
