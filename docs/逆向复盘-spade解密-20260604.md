# 红果视频 spade→key 逆向完整复盘（2026-06-04，macOS Apple Silicon）

> 本文是一次完整逆向 session 的自包含复盘：从「在 Mac 上搭 arm64 环境」到「纯离线全自动下载器」。
> 重点记录**完整过程、环境配置、踩的坑/弯路、注意点**，供复现与接力。
> 算法细节与历史进展另见 `VIDEO_DECRYPTION_RE.md` §16；本文偏「怎么做到的」。

## 0. 一句话结论

红果当前视频的 `content key` 由 **`spade_a` 经纯字节变换算出**（`libttmplayer.so` 内 `FUN_001c4550`，**无 KEK、无 AES**），已 100% 纯 Python 复现。配合 `senc` 盒里的 `base_iv` 和标准 CENC AES-128-CTR，实现**纯离线、无需播放、无需 frida 的解密**；再接红果 API 取 `spade_a`+直链，做成**全自动下载器**（仅签名一环还需模拟器跑 app）。

最终产出：
- `frida/unwrap_spade.py` —— 纯算法 `spade→key`（6 组真值自测）
- `frida/offline_decrypt.py` —— `spadeA + 密文mp4 → 明文mp4`
- `offline_dl.py` —— 全自动 `搜索→选集→下载→解密`

## 1. 目标与背景

- **要什么**：每个视频的 `content key(16B)` + `base_iv64(8B)`，用于 CENC AES-128-CTR 解密。
- **已知**：视频是标准 **CENC AES-128-CTR**（密码学层已破）；`key` 由 `spade_a`(API 下发的 base64 包装 blob) 在端上本地算出，非网络下发。
- **为什么搬到 Mac**：之前在 MuMu(x86 + Houdini 翻译层) 上 Frida 的 native backtrace 不可用，无法回溯定位 unwrap。**Apple Silicon 跑原生 arm64 镜像零翻译，backtrace 可用 = 关键解锁点**。

## 3. 完整逆向过程（按阶段）

### 阶段 1：决定性验证 —— backtrace 不再被翻译层挡
- hook JNI `GetStringUTFChars` 抓 `spade_a` 串 + `Thread.backtrace`。
- 结果：栈帧落到 **真实 ARM 模块** `libttmplayer.so+0xac9ac` / `+0x210ed4`，**无 libhoudini**。
- ⇒ arm64 镜像选对了，墙拆了，可以往下逆。

### 阶段 2：从「输出」反向定位 —— hook av_dict_set 拿 backtrace
- 关键思路：解密最终走 **ffmpeg CENC**，content key 经 `av_dict_set(dict,"decryption_key",<hex>)` 喂进去。**从这个「输出点」往上回溯**最直接。
- `av_dict_set` 的宿主模块是 **`libttffmpeg.so`**（字节自带 ffmpeg，不是 libavmdl/libttmplayer）。
- hook 它、过滤 `key=="decryption_key"`、打印模块化 backtrace：**整条调用栈全在 `libttmplayer.so`**：
  ```
  libttmplayer.so+0x1ec198 (av_dict_set 调用点) → +0x1ea070 → +0x1e09e8 → +0x1e1124 → ...
  ```

### 阶段 3：反编译里顺藤摸瓜 + 发现「两条路径」
- **⚠️ Ghidra 基址 = `0x100000`**：frida 给的模块偏移 `0xXXXXX` 对应 Ghidra 地址 `0x1XXXXX`。（用 `av_dict_set@plt` 偏移 `0x71e50` vs Ghidra `0x171e50` 校准。）
- 沿 backtrace：`FUN_001ec070`(av_dict 调用点) ← `FUN_002716e8`(frida `0x1716e8`) ← demuxer。
- `FUN_002716e8` 里发现**分流**：
  ```c
  FUN_00271964(handle, spade, &local_78, &local_80);   // 解析 spade, local_80=type
  if (strcmp(local_80,"2") != 0)  memcpy(out, local_78);          // ver1
  else                            FUN_00271a50(local_78, KEK);    // ver2: AES-GCM
  ```

### 阶段 4：踩坑 —— 先逆了 ver2（AES-GCM），结果当前视频不用
- 先以为 `FUN_00271a50` 是 unwrap，完整逆出：`base64 + MD5(KEK材料).hexdigest()作AES-256-key + AES-GCM-256-decrypt`（`FUN_00271b88` 是 `vsnprintf("%02x")` 把 MD5 转 hex）。还静态抠了固定 IV 常量、查了 opt 462(KEK材料)/opt 144(spade) 映射。
- **hook `FUN_00271a50` 却完全不触发**，但同时 hook 的 `av_dict_set` 有 content key 输出（如 `121846f9...`）。
- ⇒ **确诊：当前视频走 ver1，根本不进 AES-GCM**。`av_dict` 有输出但 ver2 不触发 = key 来自 ver1 路径。

### 阶段 5：定位真正的 unwrap `FUN_001c4550`（ver1）
- ver1 路径：`FUN_00271964 → FUN_001c4550(base64_decode(spade), len, &outkey, &outtype, flag)`。
- hook `FUN_001c4550`（frida `0xc4550`），抓到 5 组 `(spade_decoded_37B → content_key)`，**最后一组输出 = 同时 av_dict 抓到的 `121846f9...`** → 铁证。
- 读完算法：**纯字节变换**（XOR + POPCOUNT + 位置相关 + 按首字节 hex 值切片），**无 KEK、无 AES**。

### 阶段 6：纯 Python 复现 + 端到端
- `unwrap_spade.py` 复现 `FUN_001c4550`，**6 组真值（5 实时 + §16.8 历史）100% 命中**。
- `offline_decrypt.py`：`spadeA + 密文` → `unwrap_spade` 出 key + `senc` 读 base_iv + `decrypt_full` → 明文。e4 验证 hevc 540x960。
- `offline_dl.py`：接 hongguo API（签名）取 `video_model`，全自动 `搜索→下载→解密`。全新剧《汉语节目》1080p 端到端成功（4495/4495 样本合法）。

## 4. 核心算法 `unwrap_v1`（ver1，已复现）

输入 `spade = base64_decode(video_model.encryptInfo.spade_a)`（37 字节），`flag = 播放器 opt 0x97`（实测 0）：

```python
def popcount(x): return bin(x & 0xffffffff).count('1')
def s8(v): v &= 0xff; return v-256 if v>=128 else v

def unwrap_v1(spade, flag=0):                       # spade: 37B
    bVar5 = spade[0]^spade[1]^spade[2]
    iVar9 = bVar5 - 0x30                            # type 字符串长度
    uVar1 = (len(spade) - bVar5) + 0x2f            # 工作缓冲长度
    dest  = bytearray(spade[1:1+uVar1])
    # 解出 type 字符串(末尾 iVar9 字节 XOR 两个尾字节), 判断 ver1/ver2:
    #   若以 "app_v2"/"web_v2" 开头 → ver2(AES-GCM, 另一函数), 否则 ver1:
    b14, b16 = 0x55, 0xfa
    for i in range(uVar1):
        b6 = dest[i]; u18 = popcount(i)
        b3, b7 = b6, b14
        if i & 1: b3, b7, b16 = b16, b6, b14
        c = (u18+0x15) if flag else s8(-0x15 - u18)
        dest[i] = (c + (b16 ^ b6)) & 0xff
        b14, b16 = b7, b3
    # 按 dest[0] 的 hex 值 u11 切出 content key = dest[1 : uVar1 - u11]
    b0 = dest[0]
    u11 = b0-0x30 if 0x30<=b0<=0x39 else (b0-0x57 if 0x61<=b0<=0x7a else 0xffffffff)
    return bytes(dest[1 : uVar1-(u11&0xff)]).decode('latin1')   # 32 hex 字符 = content key
```

完整可运行版（含 ver2 判断、自测）见 `frida/unwrap_spade.py`。

完整解密链路：
```
content key = unwrap_v1(base64_decode(spade_a))      # 纯算法
base_iv64   = 密文 mp4 senc 盒首样本 IV 高 8 字节     # 纯文件
per-sample IV = ((base_iv64 + 样本序号) << 64)
明文 = AES-128-CTR(content_key, IV) 逐样本解密
```

## 5. 关键函数地图（`libttmplayer.so`）

| frida 偏移 | Ghidra 地址 | 函数 | 作用 |
|---|---|---|---|
| `0xac9ac`/`0x210ed4` | — | — | JNI 抓 spade 的 backtrace 帧(阶段1) |
| `0x1ec198` | `0x2ec198` | (in `FUN_001ec070`) | `av_dict_set("decryption_key")` 调用点 |
| `0xec070` | `0x1ec070` | `FUN_001ec070` | demuxer，写 av_dict |
| `0x1716e8` | `0x2716e8` | `FUN_002716e8` | **分流**：ver1 vs ver2 |
| **`0xc4550`** | **`0x1c4550`** | **`FUN_001c4550`** | **★ ver1 真 unwrap（纯字节变换）** |
| `0x171a50` | `0x271a50` | `FUN_00271a50` | ver2 unwrap（AES-GCM-256，**当前未用**） |
| `0x171b88` | `0x271b88` | `FUN_00271b88` | ver2 的 `vsnprintf("%02x")`（MD5→hex） |

> `av_dict_set` / `av_base64_decode` / `av_aes_gcm_256_decrypt` / `av_md5_sum` 是 ffmpeg 导出，宿主 **`libttffmpeg.so`**。

内部 string-key（option→key 映射在 `libttmplayer` 的 `~0x311xxx`）：`spade=opt 0x90(144)→0x7531`；`KEK材料(仅ver2)=opt 0x1ce(462)→0x7541`。

## 6. 踩的坑 / 弯路（最有价值的部分）

1. **方向误判：以为 unwrap 在 `libavmdlv2`**。早期基于二手动态描述，反编译了 `libavmdlv2`(18098 函数)找 `0x7531/0x7541`，其实真正的 unwrap 在 **`libttmplayer`**。教训：**以 av_dict_set 的真实 backtrace 为准**，别靠猜。

2. **Ghidra 基址 0x100000**。frida 偏移要 `+0x100000` 才是 Ghidra 地址，否则定位到错误函数。用 PLT 符号(`av_dict_set@plt`)的 frida 偏移 vs Ghidra 地址校准。

3. **逆错了路径（ver2 AES-GCM）白忙一场**。`FUN_00271a50` 完整逆出 AES-GCM + MD5(KEK)，结果 hook 它**完全不触发**——当前视频走 ver1。靠「`av_dict` 有输出但目标函数不触发」对比才确诊。教训：**hook 目标函数时一定同时 hook 输出点做对比**，确认走的是哪条路径。

4. **content key「缓存」假象**。一度以为 key 被缓存导致 unwrap 不触发，实际是 hook 错了 ver2。ver1 的 `FUN_001c4550` 每次播放都触发、不缓存。

5. **网络：被「不存在的域名 + fake-ip」联手误导**。用猜的域名 `v3-sdk.toutiaovod.com` 测连通，Stash 对**任何**查询(包括不存在域名)都返 fake-ip `198.18.x.x`，制造「能解析但连不上」假象，浪费很久。**红果真实视频域名是 `*.qznovelvod.com`(CNAME→`ctlcdn.cn` 电信 CDN)，不是 toutiaovod**。靠 hook `getaddrinfo` 抓出真实域名才纠正。

6. **emulator 被搞到 `adbd offline`**。反复 `am force-stop` + 多次 frida attach 把模拟器系统搞挂，`adb reconnect` 救不回，只能 `pkill qemu` 重启 emulator。教训：**别高频 force-stop + 反复 attach**。

7. **frida 17 无 Java bridge**。签名 `oracle.js` 的 `Java.use` 报 `'Java' is not defined`。降到 **16.7.19**(server+python)解决。

8. **hongguo.py 死锁**。`sign()` 在 `_oracle_lock` 锁内调 `oracle()`(再取同一非重入锁)→ 死锁。Windows 走 `SIGN_SERVER` HTTP 不触发，Mac 进程内 frida 必触发。改 `threading.RLock()` 解决。

9. **不能断代理**。本机靠 Stash 翻墙连 Anthropic API，**断 Stash = Claude 掉线**。所以解法是 Stash 的 **Fake-IP-Filter** 加 `*.qznovelvod.com`(返真实 IP) + frida `getaddrinfo` 重写到真实 CDN IP，而**不是**断代理。

## 7. 注意点（接力必看）

- **frida 必须 16.x**（签名要 Java bridge）；server 与 python 版本必须一致。
- **Ghidra 基址 0x100000**（偏移换算）。
- **签名仍需模拟器跑 app**：`oracle.js` hook `NetworkParams.tryAddSecurityFactor`（Java，平台无关，arm64 OK）。这是唯一还依赖 app 的环节；**解密本身纯离线**。
- **`spade_a` 按清晰度**：`video_model.video_list[].encrypt_info.spade_a`，每个清晰度一个；选 `video_meta.size` 最大者。
- **`base_iv` 按 track**：一个密文 mp4 有多个 `senc`(video/audio)，各自 base_iv 不同；用「能解密(NAL自证)」选出 video track 的。
- **`main_url` 有时效**（`url_expire` ~6h），过期重新调 API。
- **一个 CDN IP 按 Host 服务整个 CDN**：`*.qznovelvod.com` 任意子域名都可解析到同一个电信 CDN IP（hook getaddrinfo 重写时利用这点，一劳永逸）。
- **ver2(AES-GCM) 当前未见使用**，但代码里有（`spade` type=="app_v2"/"web_v2"）；若日后出现需补 `unwrap_spade` 的 ver2 分支。
